# pony-engine

2D-анимация в стиле MLP без хранения тысяч кадров: персонаж описывается как
модель (скелет + части + морфы + анимации) и строится в реальном времени.

## Запуск

Единая точка входа — GUI. Из корня workspace (`pony-engine/`, не из
`crates/pony-gui/` — ассеты подключены относительными путями):

```bash
cd pony-engine
cargo build --workspace
cargo run
```

`cargo run` без `-p` теперь сам запускает `pony-gui` (см. `default-members`
в корневом `Cargo.toml`) — открывается окно с персонажем, слоями, таймлайном
и скриптовой консолью (см. ниже). `pony-cli` остаётся в workspace как
внутренний диагностический харнесс (`cargo run -p pony-cli`) — печатает в
консоль профиль системы и гоняет headless-рендер в файлы; для обычной
работы он не нужен, всё то же самое видно прямо в окне GUI.

## Структура

```
pony-engine/
  crates/
    pony-core/     — модель данных (готово, компилируется)
      skeleton.rs  — кости, иерархия, world_transform; reparent/remove_subtree/
                     rename_bone — редактирование скелета с защитой от циклов;
                     world_transform_with_ik — тот же обход с применением IK
      ik.rs        — IK, Two Bone (раздел 41 ТЗ): solve_two_bone_ik —
                     аналитическое решение (закон косинусов) с Pole Target
      part.rs      — части тела (Head, Eyes, Wing, LegFL, ...), pivot, слой
      morph.rs      — именованные выражения (Smile/Sad/Blink/...) + параметры глаз
      animation.rs — ключевые кадры, дорожки, интерполяция
      camera.rs    — камера (раздел 11 ТЗ): position/rotation/zoom/shake/depth/blur
      lighting.rs  — освещение (раздел 12 ТЗ): Ambient/Sun/Point, чистая
                     функция shade_at(), без GPU; Glow/Shadow не реализованы
      orientation.rs — 2.5D-поворот (раздел 8 ТЗ): чистая функция foreshortening/parallax
      particles.rs — частицы (раздел 13 ТЗ): Dust/Snow/Rain/Spark/Magic/Smoke/Cloud,
                     чистая симуляция без GPU (эмиттер, гравитация, время жизни)
      vector.rs    — VectorDoc/VectorShape (раздел 16 ТЗ): редактируемый
                     векторный документ, сериализуется в настоящий SVG-XML
      player.rs    — AnimationPlayer: играет анимацию во времени (play/advance/apply),
                     зацикленные оборачиваются по модулю, незацикленные стопорятся на конце
      character.rs — Character целиком + save/load в .asset (RON)
    pony-system/   — детекция железа + политика ресурсов (готово, компилируется)
      cpu.rs       — логические/физические ядра (std::thread::available_parallelism + sysinfo)
      memory.rs    — доступная/общая память (sysinfo)
      gpu.rs       — список всех GPU через wgpu (любой backend), эвристика "мощности"
      policy.rs    — WorkloadPolicy: сколько потоков, сколько памяти, как раскидать по GPU
    pony-render/   — мульти-GPU рендер-кластер + реальный render pass (готово)
      lib.rs       — RenderCluster: N независимых wgpu Device/Queue, взвешенный
                     round-robin (`pick`), покрыт unit-тестами на пропорции
      renderer.rs  — Renderer: рисует части персонажа как текстурированные
                     квады, трансформированные world_transform костей;
                     render_particles() переиспользует тот же пайплайн для частиц
      texture.rs   — импорт PNG + SVG (растеризация через resvg/usvg/tiny-skia)
                     + PSD (раздел 16 ТЗ, `psd` крейт, обёрнут в catch_unwind —
                     реальный баг крейта паникует на Zip-сжатых слоях) + KRA
                     (`zip` крейт, mergedimage.png/именованный слой) + кэш
                     текстур по пути с LRU-бюджетом памяти (см. budget.rs);
                     если ассета нет/не читается — цветная заглушка (тот же пайплайн)
      budget.rs    — LruBudget: чистая (без GPU) бухгалтерия вытеснения
                     текстур из кэша по бюджету памяти, полностью тестируемая
      export.rs    — экспорт в GIF и спрайт-лист (раздел 14 ТЗ), чистый Rust
                     (`gif` + `image` крейты, MP4/WebM сознательно не реализованы)
    pony-script/   — скриптовый слой (раздел 15 ТЗ, готово, компилируется)
      commands.rs  — Command: словарь того, что скрипт МОЖЕТ сделать
                     (Move/Look/Blink/Smile/Walk, CameraMove/Zoom/Shake/...)
      engine.rs     — ScriptEngine: rhai::Engine с `pony`/`camera` объектами,
                     методы названы буквально как в ТЗ (Move/Blink/Zoom/...)
      lib.rs       — apply_commands(): применяет команды к реальному
                     Character/Camera/AnimationPlayer; скрипт сам их не мутирует
                     напрямую — pony.Walk() запускает playback через player.play()
    pony-cli/      — демо: печатает профиль системы, поднимает пул/кластер под него,
                     параллельно (rayon) считает скелет для сцены из 64 персонажей,
                     рендерит сцену из 3 персонажей через RenderCluster,
                     прогоняет пример rhai-скрипта через pony-script,
                     затем сохраняет/загружает .asset
    pony-gui/      — ЕДИНАЯ точка входа (`cargo run`), настоящее окно,
                     проверено под Xvfb: winit + egui + egui-wgpu БЕЗ eframe
                     (см. "Версии зависимостей" — eframe тянет wayland
                     принудительно). Интерфейс по структуре Adobe Animate:
                     меню + тулбар сверху, палитра инструментов слева, Stage
                     с линейками/зумом/паном по центру, Timeline снизу (слои
                     встроены в неё, сетка кадров, не времени), вкладки
                     Properties/Library/Color/Align/Transform/Info/Script/
                     Lighting/Particles справа (Lighting и Particles реально
                     управляют рендером — не заглушки, см. ниже; Transform
                     включает слайдер 2.5D-поворота персонажа целиком, не
                     только per-bone), Playback bar + Status bar в самом
                     низу — всё поверх уже готовых Renderer/AnimationPlayer/
                     ScriptEngine/Lighting/ParticleEmitter
  assets/pony/     — тестовые PNG-части (тело/голова/рог/ухо/глаз/нога) с
                     прозрачностью — сгенерированы для проверки текстурирования
  assets/pony_svg/ — тестовые SVG-части (крыло/хвост/рот) — проверяют, что
                     PNG и SVG работают вперемешку на одном персонаже
```

## Что уже работает

- **Полная интерполяция кривых**: `animation::Track::sample` считает не
  только linear/step, но и Bezier (числовое решение x(u)=t методом Ньютона),
  Hermite и Catmull-Rom (тангенсы по соседним ключам). 7 unit-тестов
  проверяют, что все режимы точно проходят через ключевые кадры и что
  Bezier ease-in-out действительно медленнее linear у краёв — `cargo test -p pony-core`.
- **Камера реально управляет рендером**: `Camera::position/rotation/zoom` и
  детерминированная `shake_offset(t)` (две несоизмеримые частоты sin/cos,
  не PRNG — одинаковый `t` всегда даёт одинаковый сдвиг) собираются в
  view-матрицу (`scale * rotate * translate`) поверх обычной ортографической
  проекции в `Renderer::render_character`. Раньше `camera.Zoom()/Shake()/
  Move()` из скрипта меняли состояние, но рендер его игнорировал — команды
  "работали" только на бумаге. Проверено не на глаз, а по размеру отпечатка
  персонажа на кадре: без изменений камеры (zoom=1.0) непрозрачная область
  47×31px, после `camera.Zoom(1.5)` — 70×46px; отношения 70/47=1.489 и
  46/31=1.484 — с точностью до пикселя совпадают с ожидаемым множителем 1.5.
  3 unit-теста на `Camera` (нулевая тряска даёт нулевой сдвиг, сдвиг
  масштабируется с интенсивностью, `zoom_by` — множитель, не присваивание).
  Тряска не хранит своё время внутри `Camera` (чистая функция от `t`) — кто
  её применяет, тот и решает, как быстро она затухает; `pony-gui` затухает
  её в игровом цикле (`shake_intensity -= dt * 0.6`).
- **Реальное текстурирование**: части сэмплят настоящие PNG (`assets/pony/*.png`,
  сгенерированы для теста — прозрачные фигуры с антиалиасингом), а не цветные
  квады. Если у части нет назначенного PNG или файл не читается, движок
  подставляет цветную заглушку 1x1 — **тот же пайплайн**, шейдер никогда не
  ветвится на "текстура/не текстура". Проверено: в отрендеренном кадре 82
  разных цвета (антиалиасинг краёв фигур, блик в глазу, полупрозрачное копыто)
  вместо 3 плоских — то есть сэмплинг реальных пикселей, а не заглушка.
- **SVG-импорт** (растеризация через `resvg`/`usvg`/`tiny-skia`, ассеты в
  `assets/pony_svg/`): каждая часть растеризуется один раз при первой
  загрузке (масштаб ×4 от viewBox, до 1024px), результат premultiplied-альфы
  от `tiny-skia` конвертируется в straight-альфу перед аплоадом на GPU —
  иначе полупрозрачные края были бы темнее, чем нужно. Персонаж в демо-сцене
  специально смешивает PNG (тело/голова/рог/уши/глаз/ноги) и SVG
  (крыло/хвост/рот) на одном скелете, чтобы проверить, что диспетчер в
  `Renderer` разводит их по правильным загрузчикам. Проверено отдельно от
  3D-сцены: растеризовал каждый SVG изолированно и сверил пиксели —
  цвета точно совпадают с заданными в исходнике (`#f2f2e8`→(242,242,232) и
  т.д.), фон честно прозрачный (alpha=0), на краях — промежуточная альфа
  от антиалиасинга.
- **Скриптовый слой** (раздел 15 ТЗ, `pony-script`): rhai-скрипт вызывает
  `pony.Move()/Look()/Blink()/Smile()/Walk()` и `camera.Move()/Rotate()/Zoom()/Shake()/Depth()/Blur()`
  — методы называются буквально как в ТЗ. Скрипт не мутирует состояние
  напрямую, а копит `Command` в очередь (через `Rc<RefCell<Vec<Command>>>`,
  расшаренный между прокси-объектами `pony`/`camera` в scope) — `apply_commands`
  применяет их к реальному `Character`/`Camera`/`AnimationPlayer` отдельным
  шагом. `pony.Walk()` не двигает кости сам — он запускает анимацию "Walk"
  через `AnimationPlayer::play()`, если она есть у персонажа (иначе — честное
  предупреждение в stderr, а не тихий no-op). Проверено 6 тестами: команды
  накапливаются в правильном порядке (три `Move(1,0)` подряд дают сдвиг на 3,
  а не перезапись), `Zoom` — множитель, а не присваивание (`Zoom(2.0);
  Zoom(3.0)` → 6.0, не 3.0), невалидный скрипт возвращает `Result::Err`, а не
  паникует, и `Walk()` либо реально запускает playback (когда анимация есть),
  либо оставляет проигрыватель в покое (когда её нет) — оба пути отдельно протестированы.
- **Проигрыватель анимаций** (`pony_core::AnimationPlayer`): `play()`/`advance(dt)`/`apply()`
  — держит текущее время, зацикленные анимации оборачивает по модулю
  длительности, незацикленные останавливает на последнем кадре (не откатывает
  и не вылетает за пределы). Применение — абсолютное (каждый тик переписывает
  канал заново), как в большинстве скелетных аниматоров. 4 теста: значение
  кости соответствует прошедшему времени, зацикленная анимация действительно
  оборачивается (`advance(2.5)` при длительности 2.0 → время 0.5, не 2.5),
  незацикленная стопорится и репортит `is_finished()`, а несуществующая
  анимация не паникует ни на `advance`, ни на `apply`.
- `cargo run -p pony-cli` реально запускается и:
  1. Определяет систему: ядра CPU, доступную память, все видимые GPU
     (в headless-контейнере без видеокарты честно нашёл программный
     растеризатор `llvmpipe` через Mesa/OpenGL и поднял под него настоящий
     `wgpu::Device` — то есть CPU-only fallback работает по-настоящему,
     а не как заглушка).
  2. Считает политику: потоки rayon = логические ядра минус один (резерв
     под основной цикл), бюджет памяти = 75% от доступной, GPU-назначение —
     один адаптер / несколько с весами по эвристике мощности (дискретный
     GPU весит больше интегрированного и программного).
  3. Параллельно (`rayon::ThreadPool`, размер = из политики) считает мировые
     трансформации скелета для 64 "персонажей" — заготовка под реальную
     параллельную анимацию сцены.
  4. Создаёт `SamplePony`, сохраняет `sample_pony.asset` (RON вместо PNG-кадров),
     загружает обратно, сэмплит анимацию.
  5. Прогоняет rhai-скрипт (`pony.Move()/Smile()/Blink()/Walk()`,
     `camera.Zoom()/Shake()/Move()`), запускает анимацию "Walk" через
     `pony.Walk()` и **реально рендерит 3 кадра** проигрывания — проверено
     не глазами, а побайтовым сравнением: кадры с одинаковым `Head.y`
     (симметрия кривой на t=0.2 и t=0.4) дают идентичный md5 пикселей,
     а кадр с другим `Head.y` (t=0.6 → wrap на 0.0) отличается на 651 байт —
     то есть анимация действительно двигает рендер, не только цифры в консоли.
- **`cargo run` — единственная точка входа, настоящее окно, не консоль.**
  Собран вручную из `winit` + `egui` + `egui-wgpu`, БЕЗ `eframe` (см. "Версии
  зависимостей" — `eframe` жёстко тянет `egui-winit`'s `"clipboard"`-фичу →
  `smithay-clipboard` → `wayland-protocols` 0.32+, требующий `edition2024`;
  ручной набор с фичами только `x11` этого избегает). GUI не изобретает
  второй рендер-путь: тот же `pony_render::Renderer`, что и в headless-демо,
  рисует персонажа в offscreen-текстуру, которая заливается в Stage через
  `painter.image()`.

  **Интерфейс воспроизводит структуру Adobe Animate**, по присланному
  описанию, а не "одна плоская панель":
  - **Меню сверху** — File/Edit/View/Insert/Modify/Text/Commands/Control/
    Debug/Window/Help. Реально работают: File → New/Save/Open (фиксированный
    путь `gui_character.asset`, без диалога выбора файла — `rfd` не собрать
    в этой песочнице, см. "Версии зависимостей")/Exit; Control → Play/Stop/
    Rewind; Window → показать/скрыть Timeline и правую панель. Остальные
    (Edit/View/Insert/Modify/Text/Commands/Debug) — честно помечены
    "не реализовано", не притворяются рабочими.
  - **Вторичный тулбар** — New/Open/Save/Undo/Redo/Publish (Undo/Redo/Publish
    задизейблены — нет истории отмены и экспорта, `ui.add_enabled(false, ..)`,
    не спрятаны и не притворяются кликабельными) + слайдер Zoom + заглушка
    Workspace-селектора.
  - **Палитра инструментов слева** — Selection/SubSelection/FreeTransform/
    Lasso, Pen/Pencil/Brush/Line/Rectangle/Oval/PolyStar, PaintBucket/
    InkBottle/Eyedropper, Hand/Zoom, плюс Stroke/Fill свотчи. Большинство —
    визуальные заглушки (движок не рисует произвольную векторную графику,
    только части персонажа с готовыми текстурами) — честно и коротко
    прокомментировано в коде. Реально работают Hand (тянет Stage) и колесо
    мыши над Stage (зум). Иконок-ассетов нет — короткие текстовые метки
    вместо пиктограмм, не выдаются за "настоящие" иконки Animate.
  - **Stage по центру** — не просто картинка на весь экран: холст с рамкой
    экспортной области (480×360, реальный размер рендера), панорамированием
    (Hand) и зумом (колесо мыши), упрощённые линейки по верхнему/левому краю.
  - **Timeline снизу** — слои встроены ПРЯМО в Timeline (как в Animate —
    Layers не отдельная панель), но сетка **кадров** (24 fps), не времени:
    линейка с номерами кадров, по одной строке на каждую часть персонажа
    (чекбоксы видимости и блокировки рисуются вручную через `Painter`, клик
    обрабатывается вычислением, в какую строку/колонку попал курсор), жёлтые
    кружки-кейфреймы в кадровых ячейках (дорожка привязывается к слою по
    совпадению кости; дорожки без такой привязки — камера/морфы — собраны в
    один ряд "Прочее", как и в Animate у них нет своего "слоя" на канвасе),
    красный плейхед на всю высоту, скраб кликом/перетаскиванием.
  - **Вкладки справа** — Properties/Library/Color/Align/Transform/Info,
    ровно как в присланном описании, плюс **Script** (движковая вкладка
    сверх набора Animate — у Animate нет скриптовой консоли rhai, это наше).
    Properties и Transform реально мутируют персонажа (Transform двигает/
    крутит/масштабирует кость выбранного слоя через `DragValue` — не
    косметика). Library честно показывает список PNG/SVG-путей персонажа.
    Color — рабочие цветовые пикеры, но **не влияют на рендер** (движок
    сэмплит готовые текстуры, не заливает векторные фигуры) — прямо
    подписано в самой вкладке. Align — подписан как нереализованный (нет
    мультивыбора объектов на Stage).
  - **Playback bar** — Rewind/Play-Pause/Step, номер кадра, FPS, заглушка
    Scene-селектора, состояние Loop (отражает `animation.looping`, не
    отдельный переключатель — честно, а не притворная кнопка), Zoom.
  - **Status bar** — активный инструмент, текущее выделение, размер
    документа, Zoom%.

  **Нашёл и исправил реальный баг раскладки в процессе**, не просто написал
  и сдал: изначально добавил боковые панели (инструменты слева, вкладки
  справа) в коде РАНЬШЕ нижних панелей (Timeline/Playback/Status) — в egui
  порядок вызовов `Panel::show()` определяет геометрию, и панель, добавленная
  раньше, посчитает своим доступным пространством ещё не обрезанную нижними
  панелями область. Результат: палитра инструментов слева растягивалась на
  всю высоту окна и перекрывалась нижними панелями. Заметил не на глаз, а по
  количеству "полос содержимого" в колонке инструментов: ожидал ~20 (16
  инструментов + разделители + свотчи), получил 7 — пересчитал перебором
  RGB-пикселей, нашёл нестыковку, поправил порядок добавления панелей
  (сначала верх/низ, потом бока, в конце Stage), пересчитал: 21 полоса,
  170 разных цветов — совпадает с ожиданием.

  Проверено количественно (в этой сессии текстовые описания скриншотов не
  возвращаются — верификация по пикселям, не на глаз): в Timeline нашлись
  ровно жёлтые кейфрейм-кружки именно в строке слоя "head" (единственного,

- **Частицы** (раздел 13 ТЗ: Dust/Snow/Rain/Spark/Magic/Smoke/Cloud,
  `pony_core::particles` + `Renderer::render_particles`): симуляция —
  чистая, без GPU (`ParticleEmitter::update`), с детерминированным
  накопителем времени рождения частиц (одинаковый `dt` всегда рождает
  одинаковое число частиц — важно для тестов и совпадает с уже
  установленным в движке принципом, см. `Camera::shake_offset`) и простым
  LCG для разброса начальной скорости (не внешняя rand-зависимость).
  **Честное упрощение**: частица не тает прозрачностью, а сжимается до
  нуля к концу жизни (`Particle::size_factor`) — так рендер переиспользует
  готовый пайплайн `Renderer` (та же текстура-заглушка нужного цвета из
  `TextureCache`, что и части персонажа) без отдельного альфа-блендинга.
  6 unit-тестов на симуляцию (рождение пропорционально `rate*dt`, в т.ч.
  что дробные накопления не теряются и не удваиваются на мелких шагах;
  смерть по истечении `lifetime`; Rain падает вниз, Smoke poднимается —
  проверено на знаке позиции, не только "не упало"; сжатие размера линейно
  от 1.0 до 0.0). Проверено и на реальном рендере (`pony-cli`, эмиттер
  Snow): число живых частиц растёт предсказуемо (7 → 15 → 22 за три шага
  по 0.5с при rate=15/с — сходится с ручным расчётом accumulator'а), кадры
  реально разные (побайтовая разница первого и последнего кадра — 57330,
  не статичная картинка), и общая площадь непрозрачных пикселей растёт
  медленнее, чем количество частиц (57→98→96), потому что старые частицы
  одновременно уменьшаются в размере — визуальное подтверждение, что
  сжатие-к-нулю действительно работает, а не только считается в памяти.
- **Автоматический поворот, 2.5D** (раздел 8 ТЗ, `pony_core::apply_yaw_2_5d`
  + `Character::facing_yaw`): вместо хранения кадров под разными углами —
  части персонажа как плоские карточки на условном поворотном круге, чья
  ширина (foreshortening) и горизонтальная позиция (parallax) пересчитываются
  из угла поворота и условной глубины (выводится из `layer` части — своего
  поля глубины в модели нет). **Честные ограничения**, не спрятаны: это
  плоские карточки, не настоящий меш — нет самозаслонения объёмных деталей,
  и после ~90° карточка не переворачивается на обратную сторону, а просто
  схлопывается до минимальной ширины (15% от исходной, чтобы не исчезать
  совсем) — для полноценного разворота на 180° нужна отдельная арт-сторона
  (спина), которой нет. 5 unit-тестов на чистую математику (`orientation.rs`,
  без GPU): нулевой поворот — тождество, 90° — клампится, но не схлопывается
  в ноль, части с нулевой глубиной не сдвигаются вообще ни при каком угле
  (только сжимаются), foreshortening монотонно убывает от 0° к 90°.
  Проверено и на реальном рендере: персонаж под 0°/45°/80° даёт ширину
  силуэта 47/33/19px — для 45° это почти точное совпадение с cos(45°)≈0.707
  (47×0.707≈33.2), а на 80° силуэт не схлопывается в линию благодаря
  параллаксу (уши/рог на другой "глубине" расходятся в стороны при повороте).
- **Экспорт в GIF** (раздел 14 ТЗ, `pony_render::export_gif`): кодирует

  разных размеров — честная ошибка, не паника; кодирование трёх кадров и

- **Экспорт в спрайт-лист** (раздел 14 ТЗ, `pony_render::export_spritesheet`):

  последнего неполного ряда — честно прозрачные (`RgbaImage` заполняется

  пустая), итоговый PNG размером ровно 1200×720 (5×240 на 4×180), пустая

  ячейка содержит 83 разных цвета (персонаж с антиалиасингом, не заглушка).
  Отдельный unit-тест собирает 4 кадра сплошных цветов в сетку 2×2 и
  проверяет и `frame_rect()` для каждого индекса (включая `None` за

- **Бюджет памяти под текстуры реально enforced** (`pony_render::LruBudget` +
  `TextureCache`): раньше кэш текстур рос неограниченно — теперь при каждой
  загрузке проверяется бюджет (в байтах, `width*height*4` на текстуру) и
  вытесняются наименее недавно использованные записи (LRU), пока сумма не
  впишется в лимит; повторное обращение к уже загруженной текстуре "трогает"
  её, защищая от вытеснения. Никогда не вытесняет последнюю оставшуюся
  запись, даже если она одна больше всего бюджета — иначе получился бы
  бесконечный цикл "загрузить-вытеснить-загрузить" каждый кадр. Сама
  бухгалтерия (`LruBudget`) — чистая структура без GPU, 6 unit-тестов
  (вытесняет самое старое первым; `touch()` защищает от вытеснения;
  никогда не трогает последний ключ; вытесняет несколько записей подряд,
  если нужно; повторная вставка того же ключа обновляет размер, не
  суммирует). `Renderer::new_with_budget(ctx, bytes)` принимает реальный
  бюджет (обычно из `WorkloadPolicy::memory_budget_bytes`, посчитанного по
  фактической памяти системы — не захардкожен). Проверено на реальном
  рендере (`pony-cli`): персонаж с PNG-частями суммарным размером ~286000
  байт отрендерен с намеренно маленьким бюджетом в 150000 байт — после
  рендера занято 133260 байт (в бюджете, не превышено — вытеснение реально
  сработало), и повторный рендер того же персонажа не падает: вытесненные
  текстуры прозрачно перезагружаются заново.

- **SubSelection и Lasso — последние два инструмента палитры, тоже
  реальные**, палитра инструментов слева закрыта целиком.
  **SubSelection** редактирует форму уже нарисованной (ещё не сохранённой)
  фигуры: клик выбирает её, и на Stage появляются перетаскиваемые узлы
  (`VectorShape::control_points()`) — у Rect это 4 угла (с противоположным
  углом, зафиксированным на месте, и клампом, чтобы перетаскивание "через"
  фигуру не вывернуло её в отрицательные ширину/высоту), у Ellipse — центр
  (двигает всю фигуру) плюс отдельные хендлы для rx и ry, у Line — оба
  конца, у Polyline/Polygon — каждая точка напрямую. Перетаскивание узла
  пишет через `set_control_point` — 6 unit-тестов, включая явную проверку,
  что противоположный угол Rect не двигается и что перетаскивание одной
  точки многоугольника не задевает остальные. **Lasso** — рамкой (drag на

- **Части персонажа теперь можно РАЗМЕЩАТЬ, а не только прикреплять**
  (`Part::pivot` + `Part::size`, общая математика в `pony_render`).
  Два структурных бага, из-за которых редактором нельзя было работать
  всерьёз, и оба были не в GUI, а в движке:
  1. **`Part::pivot` существовал в модели, но рендер его игнорировал.**
     Каждая часть рисовалась ровно в позиции своей кости, поэтому все
     части на одной кости лежали друг на друге, а нарисованную фигуру
     нельзя было поставить туда, где её нарисовали. Теперь `pivot` — это
     настоящее смещение относительно кости: поворачивается и
     масштабируется вместе с ней (часть сбоку от кости при повороте кости
     едет по дуге вокруг неё, а не остаётся приклеенной к экранным осям).
  2. **Скелет по умолчанию был вырожденным**: у ВСЕХ 23 костей стояло
     нулевое локальное смещение, то есть весь скелет схлопывался в одну
     точку. Нашёл это не по коду, а по диагностике реального hit-теста —
     вывел позиции частей и увидел `tail (0,0)`, `horn (0,-3.3)`,
     `ear_l (0,-3.3)`, `leg_fl (0,0)`. Отсюда и «пони выглядит как
     бесформенное пятно»: рисовалось-то всё правильно, просто в одной
     точке. Дал скелету реальную компоновку (шея и голова выше и вперёд,
     рог/уши на голове, плечи и бёдра разнесены по X, нога идёт вниз
     звеньями). 3 регрессионных теста: скелет должен быть протяжённым
     (>20 единиц по обеим осям), голова выше тела и копыто ниже тела,
     перед и зад по разные стороны от центра.

  Плюс `Part::size` — явный размер части, приоритетнее таблицы размеров
  по виду: нарисованная или импортированная часть отображается того
  размера, каким её сделали. 6 тестов на саму математику размещения, из
  них ключевой — **обратимость**: `pivot_for_world_position` обязана быть
  точным обратным к `part_world_position` при любом повороте и масштабе
  кости (иначе перетаскивание мышью «уплывало» бы), проверено на трёх
  разных комбинациях поворот/масштаб.

  Важно, что обе функции **публичные и общие для рендера и GUI**: раньше
  GUI считал позицию своей копией формулы, и стоило поменять рендер — как
  выделение начинало промахиваться мимо того, что нарисовано на экране.

- **Рабочий цикл редактора, замкнутый целиком**: нарисовал фигуру
  (Rect/Oval/Line/Pencil/Brush) → «Сохранить как слой» → она пишется
  настоящим `.svg` на диск, становится частью персонажа **ровно там, где

  иначе смена кости телепортировала бы её неизвестно куда), поправить

  вокруг чего оно будет вращаться. Проверено интерактивно под `Xvfb`:

  содержимым сохранённого `.svg` (`width="70" height="70"`), и с тем, где

- **Рисование/редактирование/сохранение SVG прямо в движке** (раздел 16 ТЗ,
  `pony_core::vector` + GUI-инструменты Rectangle/Oval/Line/Pencil/Brush):
  раньше SVG можно было только импортировать — теперь `VectorDoc`/
  `VectorShape` (`Rect`/`Ellipse`/`Line`/`Polyline`) дают настоящий

  (`to_svg_string()`), а не во внутренний формат движка. Замкнутый цикл:
  рисуешь на Stage → жмёшь "Сохранить как слой" → `VectorDoc` пишет реальный

  (альфа корректно уходит в отдельный `fill-opacity`, не портит hex-цвет;
  габарит документа считается по фигурам с отступом; `clear()` реально
  чистит). Отдельно — **независимая проверка через настоящий парсер**, не
  через сверку строк: сгенерированный `VectorDoc` прогнан через
  `usvg::Tree::from_str`/`resvg::render` (тот же путь, что использует

  валиден для стороннего инструмента.

  **И два настоящих бага, найденных и исправленных не в тестах, а по факту
  интерактивной проверки под `Xvfb`** — нарисовал прямоугольник, он не

  Xvfb":

     временный `eprintln!` с реальными значениями (`x: 70.0, y: 51.5, w: 0.0,

- **Убрана пиксельность рендера** — три отдельные, накладывающиеся причины,
  все три исправлены: (1) в самом render-пайплайне не было сглаживания
  вообще (`MultisampleState::default()` — 1 сэмпл), из-за чего края любой
  повёрнутой/не выровненной по осям части (хвост, наклонённая голова)
  рисовались жёсткой "лесенкой" — добавлено честное 4x MSAA (мультисемпл-
  текстура с resolve в обычную, для чтения обратно на CPU — не косметика
  поверх кадра, реальное сглаживание внутри самого рендера); (2) сцена на
  Stage показывалась с `TextureOptions::NEAREST` — при зуме выше 100%
  (обычное дело при точной работе с мелкими частями/узлами SubSelection)
  картинка расползалась жёсткими цветными квадратами, что перекрывало
  само MSAA-сглаживание — заменено на `LINEAR`; (3) базовое разрешение
  рендера сцены удвоено (480×360 -> 960×720, зум Stage по умолчанию
  соответственно уменьшен вдвое, чтобы персонаж на экране остался того
  же размера) — вместе с MSAA и LINEAR-фильтрацией даёт заметно более
  гладкую картинку на любом масштабе.
- **Таймлайн теперь редактирует все пять каналов кости, не только
  вертикальную позицию**: раньше `insert_keyframe`/`remove_keyframe` были
  жёстко зашиты на `BoneChannel::PositionY` — анимировать поворот,
  горизонтальное движение или масштаб через сетку таймлайна было
  физически нельзя, хотя модель данных (`BoneChannel::{PositionX,
  PositionY, Rotation, ScaleX, ScaleY}`) это всегда поддерживала. Теперь
  над сеткой — выпадающий список **«Канал»**: сетка показывает и
  редактирует дорожки только выбранного канала (переключение на другой

  (`Insert > Keyframe`) теперь тоже уважает выбранный канал — раньше был
  рассинхронизирован с сеткой (сетка редактировала одно, кнопка меню
  ставила ключ всегда по Y, независимо от того, что выбрано в сетке).

- **Несколько персонажей в сцене, таймлайн с двумя режимами**: раньше GUI
  умел работать только с одним персонажем — вообще никакого понятия
  "сцена из нескольких" не было. Архитектурное решение сознательно
  простое и малорискованное: НЕ переписывал все существующие обращения к
  `character`/`player` (их сотни по всему файлу — слепая замена была бы
  верным способом внести десятки тонких багов). Вместо этого `character`/
  `player` остаются активным персонажем, как и раньше — весь существующий
  код (Timeline, Bones, Properties, рисование и т.д.) работает без
  единого изменения. Остальные персонажи сцены лежат в `other_characters`,
  переключение — явный своп: текущее состояние уходит в список, оттуда же
  достаётся новое (со своим `AnimationPlayer` — у каждого персонажа
  анимация проигрывается независимо, время не сбрасывается при
  переключении).

  как и раньше, полный таймлайн активного (части/кости/ключи, всё
  описанное выше). **«Все»** — по одной строке на персонажа сцены

  активным И сразу переключает обратно в режим «Персонаж» — то самое

  проигрывания, кликнул по неактивному — переключился на него И
  автоматически вернулся в режим «Персонаж» с его собственным таймлайном

  пока он был неактивен — то есть каждый персонаж честно живёт своей
  жизнью, а не замирает при переключении).

  **Честное ограничение, не спрятанное**: на Stage в любой момент виден
  и рендерится только АКТИВНЫЙ персонаж — `Renderer::render_character`
  каждый вызов чистит канвас заново, поэтому несколько персонажей
  одновременно на одной сцене потребовали бы отдельного метода
  `render_scene`, рисующего части всех персонажей в ОДНОМ render pass
  (как уже сделано для частиц поверх персонажа) — не реализовано в этом
  проходе. Данные каждого персонажа (части, кости, анимации) при этом
  полностью реальны и редактируемы сразу, как становятся активными —
  ограничение только в одновременной ВИДИМОСТИ на экране, не в
  функциональности редактирования.
- **Полноценный `path` с узлами Безье** (разделы 8-9 ТЗ) — раньше редактор
  понимал только `rect`/`ellipse`/`line`/`polyline`/`polygon`, и это было
  самым крупным содержательным пробелом: готовые художественные SVG
  (включая демо-ассеты самого персонажа — `mouth.svg`/`tail.svg`/
  `wing_l.svg`, все нарисованные вручную через `<path>`) нельзя было
  открыть на редактирование вообще, только через внешний SVG-редактор.

  Модель (`PathNode { position, in_handle, out_handle, node_type }`,
  `NodeType::{Corner, Smooth, Symmetric, AutoSmooth}`) — ровно то, что
  требует раздел 9. Сериализация пишет честные `M`/`L`/`C` (минимальный
  набор, которого достаточно для любой комбинации прямых и кубических
  кривых — раздел 8 явно требует поддержки смешивания в одном path).
  Парсер — обратная операция — понимает весь набор команд раздела 8
  (`M/L/H/V/C/S/Q/T/Z`, и абсолютные, и относительные): `H`/`V` — как
  частные случаи `L`, `Q`/`T` (квадратичные) конвертируются в кубические
  по точной формуле (`C1 = P0 + 2/3(Q-P0)`, `C2 = P1 + 2/3(Q-P1)`) — модель
  узла хранит только кубические ручки, единое представление для всех
  кривых. `S`/`T` (сглаженные сокращения) — по стандартному правилу SVG,
  отражение предыдущей ручки относительно курсора. `A` (эллиптические
  дуги) — осознанно НЕ поддерживаются (честно возвращает ошибку, не
  портит геометрию молча) — дуги не сводятся к кубической Безье без
  приближения, отдельная задача.

  Узлы редактируются тем же SubSelection, что и остальные фигуры:
  `control_points()`/`set_control_point()` для `Path` возвращают позицию
  каждого узла и его ручки (какие есть — отсутствующие не создают
  фантомных перетаскиваемых точек), причём **перемещение самой позиции
  узла тащит обе его ручки вместе с ней** (иначе форма кривой ломалась бы
  при каждом сдвиге — раздел 9 разделяет "перемещение" узла и "изменение
  handle" как разные операции). `PathNode::sync_handles_after_drag` держит

  инструмент) — один несжатый (парсится нормально), другой с Zip-слоем

  принцип "никогда не роняем кадр", что и для отсутствующих файлов/битых
  SVG — и дополнительно подавил стандартный panic hook на время вызова,
  чтобы пользователь не видел пугающий бэктрейс для штатно обработанного
  случая (с честной оговоркой в коде: подавление hook'а — процессное, не

  соображением, если это когда-нибудь распараллелят). Оба тестовых PSD
  сохранены как фикстуры (`assets/test_fixtures/`) и используются и в
  unit-тестах (`cargo test -p pony-render` — валидный парсится и даёт точно
  тот цвет, что был при генерации; паникующий действительно ловится
  `catch_unwind`, не только "предполагается, что поймается"), и в реальном
  прогоне `pony-cli` — оба пути (успешный и упавший) не роняют программу,
  которая после них честно доходит до конца и сохраняет `.asset`.
- Формат `.asset` — RON-сериализация `Character`. Открывается текстовым
  редактором, годится для гит-диффов.
- **Реальный render pass**: `pony-cli` строит сцену из 3 персонажей
  (`Pony_A/B/C`), раскладывает их по GPU-контекстам через
  `RenderCluster::pick()` и рендерит каждого в offscreen-текстуру 320x240 —
  части рисуются как цветные квады (пока без текстур — их взять неоткуда,
  реальных PNG/SVG-ассетов ещё нет), трансформированные world_transform их
  костей. Результат сохраняется как `.ppm` (без внешних зависимостей на
  запись). Проверено: в headless-контейнере (1 GPU — программный `llvmpipe`)
  все три персонажа корректно отрисовались с ожидаемыми цветами
  тела/рога/глаз в нужных позициях — то есть путь "скелет -> GPU -> пиксели"
  работает целиком, а не только на бумаге.
- **Взвешенное распределение по GPU проверено математически**: формула
  выбора контекста (`weighted_pick_index`) вынесена в чистую функцию и
  покрыта unit-тестами — на 10 000 job'ов с весами 0.7/0.3 и на 6 000 с
  весами 0.5/0.3/0.2 распределение сходится к заданным пропорциям с
  отклонением <2%. Тестировать на настоящих двух GPU здесь не на чем
  (в контейнере только один программный адаптер), поэтому корректность
  самой формулы проверена отдельно от железа.

### Почему масштабирование именно так

Ничего не захардкожено под конкретное число ядер/видеокарт — везде считается
от факта:

- **CPU**: `std::thread::available_parallelism()` (логические) + `sysinfo`
  (физические, если нужно отличать от Hyper-Threading). Пул на всех, кроме
  одного зарезервированного потока — но не меньше одного воркера, даже на
  1-ядерной машине (проверено: контейнер, в котором собран этот проект, сам
  однопоточный, и код на нём отработал корректно).
- **Память**: берём 75% от *доступной сейчас* памяти (`sysinfo`), не от
  общей — так система не захлёбывается, если параллельно открыт браузер
  с 50 вкладками. 75% — стартовое значение, вынесено в константу
  (`MEMORY_BUDGET_FRACTION` в `policy.rs`), легко подвинуть.
- **GPU**: `wgpu::Instance::enumerate_adapters` отдаёт одну запись на КАЖДУЮ
  пару (физический GPU × backend, который его видит) — не на физическую
  карту. Одна дискретная видеокарта на Windows обычно доступна и через
  Vulkan, и через Dx12, и через GL — то есть один чип превратился бы в 3
  "видеокарты" в наивном подсчёте (плюс отдельный WARP-фоллбек
  `Microsoft Basic Render Driver` — это уже не дубликат, а настоящий
  программный запасной адаптер). `gpu.rs` схлопывает записи по PCI
  `(vendor, device)` id — стабильному вне зависимости от backend'а — и
  оставляет один, самый быстрый backend на устройство (приоритет
  Vulkan/Metal > Dx12 > GL). 0 физических GPU → `GpuAssignment::None`
  (CPU-путь), 1 → всё туда, 2+ → распределяем по весам
  (Discrete=1.0, Integrated=0.4, Virtual=0.2, Cpu(software)=0.1) —
  чтобы на связке "мощная видеокарта + встроенная графика" основная
  нагрузка шла на мощную, но слабая тоже не простаивала.
  Известное ограничение: если в системе стоят две физически ОДИНАКОВЫЕ
  карты (одинаковые vendor/device id), текущий код различит их backend'ом,
  но не сможет надёжно сопоставить конкретный физический экземпляр —
  для этого нужен PCI bus id, который в используемой версии wgpu (0.19)
  не экспонируется.
- **Мульти-GPU**: у wgpu нет понятия "рендер на несколько видеокарт
  одновременно" в одном Device — это и в реальных движках (Unreal, id Tech)
  делается вручную: N независимых Device/Queue + распределение работы
  (сцены/кадры/персонажи) между ними. `RenderCluster` именно так и устроен;
  `pick(job_index)` — взвешенный round-robin по весам адаптеров.

- **Masks/Clipping (раздел 60 ТЗ)**: `Part::clip_by: Option<String>` —
  id ДРУГОЙ части этого же персонажа, чья альфа обрезает альфу текущей
  части. Это настоящая растровая клип-маска (как маскирующий слой в
  Adobe Animate/Photoshop), не SVG `clipPath`: часть-маска САМА
  продолжает рисоваться как обычно (если маска не должна быть видна
  сама по себе — её просто не показывают отдельным видимым слоем, как
  и в Animate). `Character::resolve_clip_mask(part_id)` — единственная
  точка входа для получения активной маски части: отклоняет
  самоссылку (`clip_by == part_id`), отклоняет цепочку глубже одного
  уровня (маска сама с `clip_by` — не поддерживается, чтобы не решать
  граф циклов на каждый кадр) и битую/несуществующую ссылку — во всех
  этих случаях часть просто рисуется БЕЗ маски, не паникует и не
  скрывается целиком.

  Рендер — честный GPU-проход, не CPU-имитация: WGSL-шейдер
  (`pony-render/src/renderer.rs`) получает вторую текстуру (маску) через
  доп. bind group entries (`t_mask`/`s_mask`) и матрицу `world_to_mask_
  local = mask_model⁻¹ * this_model`, которая переводит мировую позицию
  текущего фрагмента маскируемой части в локальное [-0.5..0.5]
  пространство квада part-маски — тот же приём, что обратная матрица
  модели для сэмплинга чужой геометрии в общем шейдере, без отдельного
  прохода/stencil-буфера. Итоговая альфа = альфа part * альфа-маски *
  `in_mask_bounds` (обрезка за пределами самого квада маски через
  `step()`), либо не трогается вовсе, если `has_mask == 0.0` — быстрый
  путь без ветвления для подавляющего большинства частей без `clip_by`.
  `LoadedTexture::view` переведён с `wgpu::TextureView` на `Rc<wgpu::
  TextureView>` (единственное изменение, ломающее внутренний API
  `pony-render`, не публичный интерфейс) — маскированной части нужно
  держать ОДНОВРЕМЕННО свою текстуру и текстуру маски при сборке одного
  bind group, а `wgpu::TextureView` не реализует `Clone`.

  Проверено НАСТОЯЩИМ headless GPU-рендером (программный адаптер
  llvmpipe в этом облачном окружении, `wgpu::Instance::request_adapter`
  без моков) — два постоянных `#[test]` в `pony-render::renderer::
  mask_gpu_tests` (сами аккуратно пропускают себя, а не падают, если в
  окружении вообще нет GPU-адаптера — единственная причина пропуска):
  рендерятся реальные пиксели персонажа с частью, маскированной вдвое
  ýже неё самой, и сравниваются с контрольным кадром без маски — точка
  внутри маски остаётся видна, точка вне маски обрезается до фона, а та
  же точка БЕЗ маски видна как обычно (доказывает, что обрезание —
  заслуга именно маски, а не случайной дыры в геометрии). Второй тест
  проверяет битую ссылку `clip_by` на несуществующую часть — рендер не
  падает и не скрывает часть. Тот же сценарий воспроизведён и в
  `pony-cli` (`mask_demo`, реальный `println!`-репорт пиксельных
  значений через продовый `Renderer::render_character`, тот же путь,
  что использует GUI). В GUI — новый выпадающий список "Маска (Clip by)"
  в Properties (вкладка Part Inspector, рядом с привязкой к кости и
  порядком отрисовки): список исключает саму часть (нельзя назначить
  маску сама на себя) и части, УЖЕ являющиеся чьей-то маской (глубина
  цепочки ограничена одним уровнем, как и на рендере) — так UI не
  предлагает комбинацию, которую `resolve_clip_mask` всё равно бы
  отклонил.

- **Gradients (раздел 60 ТЗ)**: `pony_core::vector::{GradientDef,
  GradientKind, GradientStop}` + поле `VectorDoc::gradients: Vec<
  GradientDef>`. Именованные переиспользуемые определения градиента —
  тот же приём, что и `SymbolDef`/`VectorShape::Instance` (раздел 28):
  фигуры ссылаются на градиент по имени через **аддитивное** поле
  `fill_gradient: Option<String>` (на `Rect`/`Ellipse`/`Polygon`/`Path` —
  единственные фигуры с заливкой вообще; не на `Line`/`Polyline`, у
  которых заливки нет, и не на `Instance`, у которого per-instance
  градиент-override не поддержан, тот же класс ограничения, что и
  per-instance stroke override раздела 95), а не заменой типа
  существующего поля `fill: RgbaColor` на `enum`. Правка `GradientDef`
  сразу отражается на всех фигурах, ссылающихся на него по имени.
  `fill` при этом остаётся заполненным на каждой фигуре и служит: (а)
  safe-фоллбеком для потребителей, которые о градиентах не знают, и
  (б) видимым приближением цвета, пока `fill_gradient` не резолвится
  (висячая ссылка, удалённый градиент) — тот же принцип "честного
  отката", что у `resolve_symbol_instance` (символы) и
  `Character::resolve_clip_mask` (маски): битая/удалённая ссылка на
  градиент никогда не приводит к невидимой фигуре или панике, только к
  откату на плоский цвет.

  `GradientKind::Linear { x1,y1,x2,y2 }` / `Radial { cx,cy,r }` —
  координаты в object-space документа (как SVG
  `gradientUnits="userSpaceOnUse"`, не `objectBoundingBox`): один
  `GradientDef` с абсолютными координатами одинаково применяется на
  нескольких фигурах, что проще предсказать в редакторе, чем
  relative-координаты, зависящие от габарита каждой конкретной фигуры.
  `GradientDef::sample(t)` — интерполяция между двумя ближайшими
  цветовыми остановками (`GradientStop { offset, color }`, список НЕ
  обязан храниться отсортированным — `sample` сортирует сама на каждый
  вызов); честные фоллбеки на пустом списке остановок (нейтральный
  серый) и на единственной остановке (тот же цвет везде), без паники.
  `GradientDef::average_color()` — единый плоский цвет-приближение всего
  градиента (невзвешенное среднее по стопам), используется и как
  safe-фоллбек `fill`, и в GUI-превью там, где точный per-vertex
  градиент не реализован. Публичная функция `gradient_t_at(kind, x, y)`
  — чистая проекция точки на ось градиента (скалярная проекция на
  отрезок для `Linear`, доля пройденного радиуса для `Radial`), НЕ
  зажатая в `[0,1]` (зажим — забота `sample`), с честными фоллбеками на
  вырожденную геометрию (нулевая длина оси/нулевой радиус — `0.0`, не
  деление на 0/NaN).

  SVG round-trip — сериализация (`to_svg_string`) пишет каждый
  `GradientDef` в `<defs>` как настоящий `<linearGradient>`/
  `<radialGradient gradientUnits="userSpaceOnUse">` с дочерними
  `<stop offset=".." stop-color=".." stop-opacity="..">`, а
  `fill="url(#gradient_<name>)"` — только если градиент реально
  резолвится в `VectorDoc::gradients` на момент записи (иначе, опять
  же, честный откат на `fill="<hex>"`, чтобы сохранённый файл никогда не
  ссылался на несуществующий `<linearGradient>`). Парсинг
  (`from_svg_str`) читает `<linearGradient>`/`<radialGradient>` из
  `<defs>` (включая `stop-color`/`stop-opacity` и как отдельные
  атрибуты, и внутри `style="stop-color:..;stop-opacity:.."`, тот же
  каскад, что и у обычных фигур) — **порядко-независимо**: SVG не
  гарантирует, что `<defs>` с градиентом стоит раньше фигуры, которая
  на него ссылается, поэтому `VectorDoc::sync_gradient_fallback_colors()`
  пересчитывает честный `fill`-фоллбек всех фигур уже ПОСЛЕ полного
  разбора документа, а не в порядке обхода узлов (тот же публичный
  метод GUI обязана вызвать после `upsert_gradient`, чтобы правка
  градиента из панели сразу обновила фоллбек-цвет фигур на холсте).
  `<linearGradient>`/`<radialGradient>` без `id` или без единого
  `<stop>` — не тихо отбрасываются, а попадают в `VectorDoc::
  unsupported`, тот же принцип, что и у символов без `id`.

  Известное принятое ограничение: `transform_shape` (применяется при
  резолве `Instance` в конкретные фигуры символа) намеренно **роняет**
  `fill_gradient` на трансформированной копии (оставляя последний
  известный плоский `fill`) — градиент в абсолютном document-space
  визуально "отвязался" бы от трансформированной геометрии
  символьного инстанса (сдвиг/поворот/масштаб/зеркало символа не
  переносится на координаты градиента), тот же класс ограничения, что
  и per-instance stroke override.

  Рендер в GUI (Stage-превью) — честный per-vertex градиент, не
  плоское приближение: `draw_vector_shape_preview` строит `egui::
  epaint::Mesh` с цветом каждой вершины, посчитанным из её
  document-space координат через `gradient_t_at` + `GradientDef::
  sample` (`shape_fill_color_fn`), а не рисует фигуру одним `Color32`.
  Триангуляция — ear-clipping (`triangulate_fill`) для `Rect`/

  неверно рисовал невыпуклые полигоны — побочным эффектом это заодно

  32-сегментный центр-веерный fan для `Ellipse` (заменил прежнюю
  approximation "рисовать как круг", которая игнорировала `rx != ry`).
  Реальный SVG-рендер (не GUI-превью) проверен настоящим resvg/
  tiny-skia растром: `pony-render::texture::vector_roundtrip_tests::
  drawn_gradient_ellipse_renders_the_correct_stop_color_through_a_real_svg_parser`
  сериализует градиентную фигуру, парсит получившийся SVG настоящим
  `usvg`/`resvg`, растеризует и сверяет пиксель в центре градиента с

  градиент в sRGB-корректном пространстве, не в наивном линейном RGB,
  как `GradientDef::sample`, так что точное совпадение не ожидается и

  В GUI — новая вкладка **Gradients**: форма создания/редактирования

- **Boolean-геометрия (раздел 44 ТЗ, меню Modify -> "Combine Paths")**:
  `pony_core::boolean::{BooleanOp, boolean_op, flatten_shape_to_contour,
  piece_to_shape}` — Union/Difference/Intersection/XOR/Divide между двумя
  произвольными фигурами документа. Реализовано через настоящий
  проверенный сканлайн-движок полигонального оверлея `i_overlay`
  (в духе Vatti/Martinez-Rueda), а не собственная наивная реализация —
  чистый Rust без транзитивных зависимостей вне workspace, тот же класс
  библиотеки, что раньше отмечался как нужный в списке пробелов
  ("обычно решается через полигональную триангуляцию или библиотеку
  вроде `lyon`/`boolean-ops`").

  Сам движок оверлея работает с полигонами (прямыми отрезками), не с
  кривыми — поэтому перед операцией фигура сначала ФЛЭТТЕНИТСЯ:
  `Rect`/`Polygon` — точно, `Ellipse` — 32-сегментная аппроксимация (тот
  же приём, что и в GUI-превью), закрытый `Path` — кубические сегменты
  между узлами семплируются по параметру `t` с тем же выбором "прямая
  линия vs. кривая", что и у сериализации в SVG `path_data_string`
  (сегмент — прямая, только если у ОБОИХ узлов нет ручки со своей
  стороны). `Line`/`Polyline`/`Instance`/незамкнутый `Path`/`Polygon` с
  менее чем 3 точками не флэттенятся вообще (`None`) — та же честная
  фильтрация, что и у остальных заливка-специфичных операций
  (`set_fill_gradient` и т.п.), не паника на неподходящей фигуре.

  Результат — один или несколько `VectorShape::Polygon` (не кривая):
  обратное преобразование "полигон -> гладкий Path" не является целью
  этой задачи. `Difference` не симметрична (вычитает нижнюю фигуру из
  верхней — порядок важен), `XOR` возвращает по куску на каждую
  исходную фигуру (её часть, не покрытая другой), каждый кусок сохраняет
  ЦВЕТ своей исходной фигуры (честнее плоской заливки одним цветом на
  весь результат), `Divide` (поведение как в Illustrator/Animate) режет
  обе фигуры на все непересекающиеся куски СРАЗУ — "только верхняя",
  "только нижняя" и "перекрытие" (кусок перекрытия красится стилем
  верхней фигуры — она визуально перекрывает нижнюю в этой зоне на
  исходном холсте).

  Честное принятое ограничение: `VectorShape::Polygon` хранит только ОДИН
  замкнутый контур (нет встроенной поддержки дырок/`fill-rule: evenodd`)
  — если результат содержит "дырку" (например `XOR` двух концентрических
  фигур), внутренний контур отбрасывается и остаётся только внешняя
  граница куска; это явно репортится вызывающей стороне через
  `BooleanResult::dropped_holes` и показывается пользователю в
  status-баре GUI, а не тихо теряется.

  В GUI — новая вкладка **Combine Paths**: список подходящих фигур
  документа (только те, что реально флэттенятся), два выпадающих списка
  "Верхняя фигура (front)"/"Нижняя фигура (back)", выбор операции,
  кнопка "Выполнить" — заменяет обе исходные фигуры результатом
  (удаляются по убывающему индексу, чтобы не сбить нумерацию друг
  друга).

  15 unit-тестов в `pony_core::boolean::tests`: флэттенинг каждого типа
  фигуры (включая честные `None` для Line/Polyline/Instance/вырожденного
  Polygon/открытого Path), флэттенинг Path с ручками действительно даёт
  кривую (не прямую), Union/Intersection/Difference с проверкой площади
  результата по формуле шнурков (независимый способ сверки, не завязан
  на порядок точек, который отдаёт `i_overlay`), несимметричность
  `Difference` (`A - B` != `B - A`), пустой (не паникующий) результат
  `Intersection` для непересекающихся фигур, `XOR` даёт 2 куска каждый
  со своим исходным цветом, `Divide` даёт 3 куска суммарной площадью,
  равной `Union` (геометрически: та же область просто разрезана иначе),
  кусок перекрытия у `Divide` красится стилем верхней фигуры,
  `boolean_op` возвращает `None`, если хоть одна фигура не флэттенится,
  `piece_to_shape` строит `Polygon` без градиента.

- **Symbols / переиспользуемые компоненты (раздел 28 + 95 ТЗ)**:
  `VectorDoc::symbols: Vec<SymbolDef>` — именованные переиспользуемые
  определения (`SymbolDef { name, shapes }`), на которые ссылаются сколько
  угодно `VectorShape::Instance` через собственный 2x3-transform (позиция/
  поворот/масштаб/отражение) и опциональный `fill_override`. Ключевое
  свойство раздела 28 ("Обе копии ссылаются на один Symbol Definition") —
  правка `SymbolDef` отражается на ВСЕХ инстансах сразу: `resolve_symbol_
  instance()` резолвит инстанс в конкретные фигуры каждый раз заново из
  актуального определения, не из закэшированной копии геометрии. Пример
  из ТЗ (Eye -> Eye_L/Eye_R зеркалированием через `scale_x: -1`) —
  реализован буквально: `transform.0` (компонента `a` матрицы)
  отрицательная у одного инстанса, положительная у другого, оба ссылаются
  на один `SymbolDef "eye"`.

  Раздел 95 ("Symbol instance overrides"): `fill_override` — override
  заливки конкретного инстанса, не трогает `SymbolDef` и не виден на
  остальных инстансах того же символа (per-instance stroke override не
  реализован в этом проходе — раздел 95 описывает override именно для
  заливки/стиля, отдельная задача при первом реальном запросе). "Modify ->
  Break Apart Symbol" — `VectorDoc::break_apart_symbol_instance(index)`:
  разрывает связь конкретного инстанса, заменяя его на независимую
  inline-копию геометрии символа (с уже применённым transform/override) —
  дальнейшая правка `SymbolDef` на неё больше не влияет, как требует
  раздел 95.

  Сериализация — настоящий SVG-механизм переиспользования, не инлайн-
  копирование: `to_svg_string()` пишет каждый `SymbolDef` один раз как
  `<symbol id="symbol_<name>">` внутри `<defs>`, а каждый `Instance` — как
  `<use href="#symbol_<name>" transform="matrix(...)">` (override заливки
  — через `style="fill:...;"` на самом `<use>`, обычный CSS-каскад SVG).
  `resvg` (уже используемый этим движком для финального рендера, см.
  `pony-render`) понимает `<use>` нативно — сохранённый .svg рисует символ
  ПРАВИЛЬНО реальным SVG-инструментом, не только внутри этого редактора.
  `from_svg_str()` читает обратно: `<symbol>` внутри `<defs>` становится
  `SymbolDef` (без `id` — предупреждение в `unsupported`, не тихая
  потеря), `<use href="#...">` (и старый `xlink:href` для совместимости
  со старыми экспортёрами) — становится `Instance`; вложенные
  инстансы-в-символах поддержаны рекурсивно с защитой от бесконечной
  рекурсии на некорректных данных (символ, ссылающийся сам на себя) —
  `depth_budget`, безопасный обрыв вместо паники/зависания.

  В GUI — новая вкладка **Symbols**: "Convert to Symbol" (превращает
  выбранную SubSelection-фигуру в `SymbolDef` + заменяет её на `Instance`
  на холсте), список существующих определений с числом активных
  инстансов и кнопкой "+ Разместить инстанс" (по центру текущего viewBox,
  `VectorDoc::new_instance_centered_at`), и "Break Apart Symbol" для
  выбранного инстанса. Превью на Stage резолвит инстансы через

  неотличимо от инлайн-копии той же геометрии.

  20 unit-тестов (`pony-core::vector::tests`): трансляция/зеркалирование
  через отрицательный масштаб, fill override не трогает определение,

- **IK — Two Bone (раздел 41 ТЗ)**: новый модуль `pony_core::ik`
  (`solve_two_bone_ik`) решает классическую задачу "Hip->Knee->Hoof,
  Hoof тянется к Target" аналитически, законом косинусов (тот же подход,
  что в Spine/DragonBones/Unity Animation Rigging) — без итеративного
  солвера, точное решение за одну оценку. `Pole Target` (раздел 41)
  реально управляет стороной сгиба колена (проверено тестом: pole по
  разные стороны линии root->target даёт противоположный знак угла
  сгиба, не декоративный параметр). Недостижимая цель (дальше
  `len_root + len_mid`) не роняет солвер в NaN — нога честно вытягивается
  максимально прямо в её сторону.

  `Skeleton::world_transform_with_ik` — новый метод поверх обычного FK
  `world_transform`: без активных констрейнтов это буквально тот же путь
  и та же цена (быстрый выход в самом начале функции — существующие
  персонажи без IK не платят вообще ничего), с констрейнтами — решает
  IK по уже посчитанной FK мировой позиции `root` (значит IK-нога может
  висеть на анимированном/качающемся родителе) и подставляет результат
  как локальные углы в копию скелета. `weight` (0..1, раздел 94:
  constraints со смешиванием) — честная угловая интерполяция по
  кратчайшему пути (`lerp_angle`), не наивный lerp по радианам, который
  ломался бы на границе ±π.

  `Renderer::render_character` теперь берёт мировую позицию частей через
  `world_transform_with_ik`, не голый `world_transform` — то есть IK
  реально двигает то, что рисуется на экране, не только цифры в тестах.
  В GUI — новая секция **IK (Two Bone)** во вкладке Bones: список
  констрейнтов с чекбоксом `enabled`, полями Target X/Y, слайдером
  Weight, опциональным Pole Target, и форма создания нового констрейнта
  (выбор Root/Mid/Tip из выпадающих списков по существующим костям).

  **Настоящая находка при разработке, поймана тестами, не спрятана**:
  первая версия солвера предполагала, что угол 0 у кости — это
  направление вдоль мировой оси +X, но в этом скелете кости направлены
  как угодно (нога дефолтного пони идёт вдоль -Y) — из-за этого IK
  на синтетической тестовой цепочке работал, а на РЕАЛЬНОМ скелете пони
  сгибал ногу не в ту сторону (Hoof оказывался ДАЛЬШЕ от target после
  применения IK, чем до — 20 вместо 14.14 при прямом расчёте). Поймано
  регрессионным тестом на настоящей геометрии `default_pony_skeleton`,
  не только на упрощённой цепочке. Вторая находка — той же природы:
  солвер сперва брал длину звена из декларативного поля `Bone::length`,
  но в этом скелете `length` не гарантированно совпадает с фактическим
  геометрическим расстоянием между костями (`UpperLegFL.length == 12.0`,
  но реальное расстояние Shoulder->UpperLeg — 7.0) — из-за этого нога не
  дотягивалась до достижимой цели (расстояние 2.74 units вместо
  ожидаемых <0.1). Исправлено: длина звена теперь считается из
  фактических мировых позиций костей (`world_transform`), не из
  `Bone::length`. Оба бага исправлены и закреплены отдельными
  регрессионными тестами, которые эти же случаи и поймали.

  12 unit-тестов (`pony-core`, модули `ik` и `skeleton::ik_integration_
  tests`): полностью выпрямленная нога даёт нулевой угол колена, цель

## Известная проблема сборки на Windows: link.exe падает

На Windows со сборкой этого проекта (и даже с отдельными базовыми крейтами
вроде `proc-macro2`/`syn`/`libc`, не связанными с этим кодом вообще)
воспроизводится падение `link.exe` с сообщениями вида `missing operand
after '\377\376'` или `extra operand '...rcgu.o'`. Диагностировано: это не
ошибка в коде проекта — линковщик падает уже на сборочных скриптах базовых
крейтов, ДО того, как дело доходит до `pony-*`. `\377\376` в восьмеричном
виде — это `0xFF 0xFE`, UTF-16 LE BOM; `link.exe` не может корректно
прочитать длинный список аргументов, который `rustc` передаёт ему через
response-файл. Похоже на повреждённую установку MSVC Build Tools.

Что помогает, по приоритету:
1. Переустановить компонент "Desktop development with C++" через Visual
   Studio Installer (снять и заново поставить галку — принудительно
   переустанавливает `link.exe`).
2. Если не поможет — обойти MSVC-линковщик целиком через `rust-lld`:
   `rustup component add llvm-tools-preview`, затем в
   `.cargo/config.toml` проекта:
   ```toml
   [target.x86_64-pc-windows-msvc]
   linker = "rust-lld.exe"
   ```
3. Перенести проект из-под `Documents` (часто под OneDrive, который может
   блокировать файлы во время синхронизации) в путь вроде `C:\dev\...`.
4. Проверить свободное место на системном диске.

## Версии зависимостей — и почему `wgpu`/`rayon` не последние

Все чистые Rust-крейты подняты до актуальных на сегодня версий:
`serde` 1.0.229, `ron` 0.12, `glam` 0.33, `thiserror` 2.0, `sysinfo` 0.30
(последний патч линейки), `pollster` 1.0, `bytemuck` 1.25. Та же история и с
`image` (импорт PNG) — используется 0.24 (последний патч линейки), потому что
0.25+ тоже тянет зависимость с `edition2024`. `resvg`/`usvg` (SVG) — 0.44,
тот же потолок (0.45+ тянет `image-webp`, которому нужен rustc 1.80+; 0.46+
у `usvg` уже сам требует `edition2024`); `tiny-skia` 0.11 идёт с ними в паре
без проблем. `rhai` (скриптовый слой) и `gif` (экспорт) — оба приятное
исключение: последние версии (`rhai` 1.25.1, `gif` 0.13.3) собираются без
единой правки, никакого `edition2024` там нет. Проверено сборкой
и прогоном — без единого warning'а.

`wgpu` (0.19) и `rayon`/`rayon-core` (1.8.1 / 1.12.1) — нет: это жёсткий
потолок именно ЭТОЙ песочницы, где собирался проект (Ubuntu 24.04, `rustc`
только через apt, версия 1.75). Начиная с `wgpu` 0.20 и с `rayon-core` 1.13
их манифесты требуют Cargo-фичу `edition2024`, для которой нужен
`cargo ≥ 1.85` (стабилизирована в Rust 1.85, февраль 2025) — а взять более
новый `rustc` здесь неоткуда: у песочницы нет доступа ни к
`static.rust-lang.org`, ни к `sh.rustup.rs`, только `apt`, который для
Ubuntu 24.04 не поднимается выше 1.75. Я проверил это явно (пробовал
`wgpu` 0.20–0.25 и `sysinfo` вплоть до 0.35 — все тянут зависимости с
`edition2024`), а не просто предположил.

**На твоей машине это не ограничение** — если там современный `rustc`
(1.85+), просто подними версии в `Cargo.toml`:
```toml
wgpu = "30"          # актуальная на момент правки; API сильно другой
rayon = "1"          # уйдёт индексmap/rayon-core пины можно снять
```
и убери пины `rayon-core`/`indexmap` из `pony-system/Cargo.toml` — они там
только ради этой песочницы. Учти: `wgpu` 0.19 → 30 — это огромный прыжок
(проект сменил схему версионирования, `0.x` → просто `x`), API `Instance`/
`Device`/`enumerate_adapters` могли заметно поменяться. Я не могу
скомпилировать и проверить этот переход здесь физически — если будешь
поднимать `wgpu`, дай знать, разберём миграцию по ошибкам компилятора
на месте.

## Почему так

- **RON + serde** вместо своего бинарного формата — читаемо, легко дебажить,
  меньше кода на старте. Если понадобится компактность/скорость — потом можно
  добавить бинарный формат (bincode) без изменения структур.
- **glam** для векторной математики — стандарт в rust-геймдеве, дружит с wgpu.
- **thiserror** — чтобы ошибки чтения/записи asset-файлов были типизированы,
  а не строками.
